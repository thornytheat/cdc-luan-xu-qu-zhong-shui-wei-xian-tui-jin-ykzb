业务背景、五条核心规则、演示步骤与样例埋点（展开看长说明）

使用者：数据集成组（离线同步任务 + 变更评审）。 现在最痛的三件事：

  • 重复事件无法分辨真假。上游重发同一版本时，无法一眼看出是「同内容重投」还是「同版本被改写」， 前者应静默丢弃，后者必须人工裁决。
  • 迟到事件把结果改坏。乱序到达的老事件如果直接覆盖，会把已经推进的行写回旧值； 而删除墓碑之后的低版本插入，更是会让已删除的键「复活」。
  • 水位线说不清能不能落库。没有统一口径的 watermark，就无法判断哪些键已经闭合、 可以安全提交或清理墓碑。

输入：每表 60 条 CDC 事件（pk / version / ts / op / after / schema_version）， 外加目标表结构 v1 与变更申请 v2。 替代：原来靠人工比对 + 一次性脚本的「去重 / 冲突裁决 / 墓碑判定 / 水位线 / 变更放行」五段判断， 现在是可单测的纯函数与可下载快照。 输出：每表最终行与墓碑、冲突逐条依据、迟到位置、水位线与未闭合键、 schema 门禁结论，以及一份 JSON 快照（交给下游装载与评审存档）。

五条核心规则（后端真算，可单测）

  1. 同键合并：同 pk 只保留最大 version；同版本且 after 完全一致 → 静默去重，不计冲突； 同版本但内容不同 → conflict，保留先到内容并列出两条事件。
  2. 删除墓碑：op=d 且版本高于后续 c/u → 键判删除；墓碑必须保留； 墓碑后到达的低版本 c/u 一律忽略并计入 ignored_after_tombstone。
  3. 乱序与迟到：按到达顺序处理，ts 小于「当前已处理最大 ts」即为迟到； 迟到事件仍按版本规则参与合并，并记录表名 + 文件行号。
  4. 水位线：watermark = min(每个键已处理事件的最大 ts)， 水位线及以下的键视为已闭合，输出全局/分表水位线与未闭合键数。
  5. Schema 门禁：新增 nullable 列 → 可放行；新增列带默认值 → 放行 + 回填； 删列 / 类型收窄 / 新增非空无默认 / 可空收紧为非空 → 阻断，每条给理由与列位置。
